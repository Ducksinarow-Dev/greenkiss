## In progress / just fixed

- ~~Data-safety pass: concurrent-write collisions + backup restore~~ — **shipped 2026-08-04**. Two independent silent-data-loss bugs, both reproduced before fixing. **(1) Restore destroyed the backup it was restoring.** `runBackup`'s filename stamp is second-resolution and `gzopen(…,'wb9')` truncates, and `backup_restore` took its safety snapshot *before* reading the target — so when both landed in the same clock second the snapshot overwrote the file being restored, and the restore then applied the already-broken current state and returned `{"ok":true}`. `runBackup` now never overwrites an existing snapshot (suffixes `_1`, `_2`, still matching the `gk_[0-9_]+` filename validation), writes via `.part` + `rename` with a byte-count check so a partial write can't masquerade as the newest good backup (which also used to suppress `maybeAutoBackup` for 24h), and `backup_restore` reads the target before snapshotting. Destructive callers (`backup_run`, pre-restore, pre-deploy) go through `runBackupOrFail` and surface a JSON error; `maybeAutoBackup` deliberately swallows failures so a full disk can't make the whole app unwritable. **(2) `collectionUpsert` lost updates under concurrency.** It was `SELECT` → merge in PHP → write with no transaction or row lock, so simultaneous writers both read the same list and the second write dropped the first. The "seed the 12 standard sections" button fires 12 unawaited `category_save` calls and kept **4 of 12** categories. New `kvMutate($pdo,$key,$fn)` wraps every read-modify-write in a transaction with `SELECT … FOR UPDATE`; the `INSERT IGNORE` that guarantees a row to lock must run *outside* the transaction, because doing it inside and upgrading to `FOR UPDATE` is a lock upgrade that InnoDB resolves by killing a transaction (measured: 5 of 12 writes dying with SQLSTATE 40001). Retries on deadlock (1213) / lock-wait-timeout (1205) with jittered backoff, since these writes are fire-and-forget from the browser and an aborted transaction *is* data loss. `sop_save`, `revision_restore`, `ack_save` and `ics_token_get` all route through it. A `set_exception_handler` now returns JSON on an escaped error — previously a PHP fatal printed into a response that still read as **HTTP 200** (the `Content-Type` header is sent at the top of the file) and leaked the server path, so a failed write looked like success to the client. **Stale-array writes.** `deleteSOP` filtered its own login-warmed cache and shipped the remainder as a whole-array `kv_set`, wiping any SOP a coworker created since that tab loaded; same shape for the three cascades. New per-record actions `sop_delete`, `doc_item_save`/`doc_item_delete` (allowlisted to `imagerepo`/`toolsPrompts`/`playbook` via `docListField`, so it can't be aimed at `tasks`) and `nav_access_save`; the category→sops, project→tasks and campaign→content cascades run server-side via `collectionMapAll` and echo both collections back, which the client applies through `_applyServerCollections`. Image Repository, Tools & Prompts and Playbook pages now write one item at a time — Image Repository especially, since `DEFAULT_NAV_ACCESS` makes it the one section every staff member has. **Cache staleness.** The kv cache was warmed once at login and never again; `refreshCache()` re-pulls on tab focus and bumps `dataVersion` in App.jsx (state bump, not a remount, so open editors and scroll survive). **Export gap.** `EXPORT_KEYS` was silently missing `imagerepo`, `toolsPrompts`, `tags`, `alerts`, `taskTemplates`, `navAccess`, `salesTargets`, `playbookRevs` — anyone using Download-full-export as their backup was losing the entire Image Repository. Left whole-doc on purpose: playbook reorder and full-document restore, and `salesTargets` — losing those races costs an ordering or a 12-number settings form, not content. Checks: `scripts/test_concurrent_writes.sh` (13 assertions) and `scripts/test_backup_restore.sh` (15); the latter fails 7 against the pre-fix code. Verified through the real production build served next to `api.php`: every path above exercised in a browser with a second user writing concurrently via the API.

- ~~**#39: Off-site backup copy**~~ — **shipped 2026-08-04 (v0.1.27)**. `backups/` sat on the same cPanel account as the database, so one deleted or compromised account lost both copies. ## Notes for whoever picks up #41 (the kv_store → real tables migration)

Greenlit by Hayden 2026-08-04 to do **before go-live**, precisely because there's
almost no real data at risk yet. That window closes when staff start using it
for real, so this is time-sensitive in a way the rest of the backlog isn't.

**Start by reading** `kvMutate()` in `api.php` and the `_SERVER_COLLECTIONS` /
`_applyServerCollections` pair in `src/globals.js`. Those two are the current
concurrency story and they're what gets deleted at the end.

**Suggested order** (each step independently shippable, so a bad one is
revertable without unwinding the whole thing):

1. Schema first, no behaviour change. Add the tables alongside `kv_store`;
   don't drop anything. `id` PK, real columns only for what's filtered or
   sorted (`status`, `assignee_id`, `due_date`, `project_id`, `publish_date`),
   plus a `data JSON` column for the long tail. Resist modelling all 30 fields
   of `ContentItem` — the JSON column is what keeps this from becoming a
   week of schema design.
2. A re-runnable migration script (`scripts/migrate_kv_to_rows.php`), safe to
   run twice, that copies one collection at a time and **leaves `kv_store`
   untouched** so it stays the rollback.
3. Convert one collection end-to-end — `tasks` is the right first one: highest
   write volume, and `task_save`/`task_delete` are the simplest actions.
   Ship it. Confirm `scripts/test_concurrent_writes.sh` still passes (it asserts
   behaviour, not storage, so it should pass unchanged — if it doesn't, the
   behaviour changed and that's the bug).
4. Then the rest, one at a time. `doc_blocks` for imagerepo/toolsPrompts/
   playbook pages last, since those are the least contended now that per-item
   writes landed.
5. Only once everything's converted: delete `collectionUpsert`,
   `collectionDelete`, `collectionMapAll`, and `kvMutate`. Keep `kv_store` for
   genuine single values (`salesTargets`, `lastDeploy`, `icsTokens`). Move
   `navAccess` onto the `users` table.

**Do #40 (optimistic concurrency) as part of step 1**, not afterwards — the
`version` column is free to add while you're already writing the schema, and
retrofitting it across every table later is pure rework.

**Two traps, both already paid for once:**
- Any read-modify-write still needs a row lock. Rows make *different-record*
  writes safe automatically; they do nothing for two writers on the same row.
- `SOPEditor` autosaves every 500ms. Conflict-check on explicit close/save
  only, or the 409 will fight the autosave loop.

**Keep both test scripts green throughout** — `scripts/test_concurrent_writes.sh`
and `scripts/test_backup_restore.sh`. The second matters more than it looks:
`runBackup` and `restoreFromBackupData` both enumerate tables explicitly, so
**every new table has to be added to both** or backups will silently stop
covering the data that moved out of `kv_store`. That is the single most likely
way this migration loses data.
